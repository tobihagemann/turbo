# Codex Edition

This directory is the Codex edition of Turbo. The root [`AGENTS.md`](../AGENTS.md) covers project-wide context; this file adds edition-specific rules.

- Read [`SKILL-CONVENTIONS.md`](SKILL-CONVENTIONS.md) before editing any skill or doc in this tree — it has the prescriptive rules. Harness facts live in [`skills/write-skill/references/harness.md`](skills/write-skill/references/harness.md).
- Use Codex-native vocabulary and tool contracts. Do not introduce Claude Code control primitives such as `TaskCreate`, `TaskList`, `AskUserQuestion`, or Claude Agent tool instructions except inside explicit mapping docs.
- This directory is the root of the `turbo` Codex plugin: skills under `skills/`, the `SessionStart` hook under `hooks/`. Users install it from the marketplace at `../.agents/plugins/`. Codex copies it into a versioned cache, so a skill resolves its own directory from the `SKILL.md` it was loaded from.
- `$peer-review` is the stable abstraction; in this edition it delegates to Claude through `$claude-print`.
- Claude-specific changes belong under [`../claude/`](../claude/), not here.
- When changing a skill, convention, addition, plugin hook, or setup/update file here, mirror the change to the parallel file in [`../claude/`](../claude/), where the plugin hook's counterpart is the plugin mod. Translate vocabulary via [`../claude/docs/harness-vocabulary.md`](../claude/docs/harness-vocabulary.md). The two editions track each other behaviorally; vocabulary differs but principles stay aligned. Drift between editions is the most common failure mode. A capability one harness lacks is not drift: mirror the principle, never this harness's ceiling. When a rule exists to work around a constraint only Codex has, the Claude sibling keeps the unconstrained form and the difference is recorded as an intentional divergence below. Narrowing a Claude gate, option set, or loop to match a Codex limit costs a real behavior there and does not count as alignment.
- After mirroring, run [`$claude-print`](skills/claude-print/SKILL.md) to have Claude review the Claude sibling against `../claude/SKILL-CONVENTIONS.md` and `../claude/CLAUDE.md`. Instruct it to read those conventions and the changed files and report findings directly, the way `$write-skill` reviews a skill, without invoking `/review-code` or any other skill. Review skills carry user-input gates that a non-interactive run drops, stalling it. Independent cross-edition eyes catch vocabulary leaks and behavioral drift the same-edition reviewer cannot see. Treat findings the same as a same-edition review (evaluate, apply).
- **Intentional divergence — crash retry:** `/codex-exec` in the Claude edition retries once when a run dies producing no output. `$claude-print` has no such rule. The evidence is codex-process-specific, and `$claude-print` Step 3 polls a shell session rather than observing a process, so a retry trigger there would license the premature give-up that Step 3 exists to prevent. Add one only if a `claude -p` crash-without-output is actually observed.
- **Intentional divergence — plan continuation:** child skills here restate a parent workflow's remaining steps in their own `update_plan` call and close with a plain `update_plan` line, where the Claude edition calls `TaskList`. `update_plan` is write-only and replaces the whole list, so a child that lists only its own steps erases the parent's and nothing can read them back; `TaskList` retrieves real stored state, so the Claude form has neither problem. Do not "resync" these to the `TaskList` phrasing when mirroring.
- **Intentional divergence — consultation option budget:** `request_user_input` allows 3 options per question while the Claude edition's `AskUserQuestion` allows 4. Where a gate's concrete choices already fill the budget, this edition presents the consultation option in place of whichever option fits least and gives the displaced option an explicit freeform path in the step that consumes it; the Claude edition simply adds a fourth option. `$apply-findings`, `$draft-plan`, `$discuss-change`, `$resolve-pr-feedback`, `$create-project-skills`, `$simplify-code`, and `$assess-technical-debt` differ from their Claude siblings for this reason. Both editions displace at `$update-dependencies`, whose strategies already fill either budget. Do not "resync" these to the Claude form when mirroring.
- **Intentional divergence — loop autonomy:** `$polish-code` and `$refine-plan` run their re-run loops to natural convergence, without the iteration hard cap, the skip/continue `request_user_input` gates, or the handoff-then-compact gate on a low-context signal that the Claude edition keeps; `skills/write-skill/references/workflows.md` and `skills/write-skill/references/tools.md` teach the autonomous form to match. This is deliberate — `request_user_input` does not reliably reach the user in Codex's non-interactive modes, so these loops rely on their own convergence signal instead. `$implement` Step 7 omits, for the same reason, the handoff-then-compact gate its Claude sibling carries ahead of QA. Do not "resync" them to the capped/gated Claude form when mirroring.
- **Intentional divergence — gate fallback:** `$smoke-test`, `$exploratory-test`, and `$investigate` write nothing and report the approval as unresolved when their external-write gates cannot reach the user. `$investigate` also stops and reports the way forward as unresolved when its reproduction gate cannot reach the user. `$polish-code` and `$refine-plan` start a fresh ledger and delete nothing when their discovery question cannot reach the user, and `$polish-code` halts with its ledger in place, reporting the differing paths, when a pending smoke-test baseline or a failed tree restore needs a decision it cannot ask for. The Claude siblings have no such rules: `AskUserQuestion` always reaches the user from the main conversation, while Codex drops `request_user_input` in non-interactive modes. The external-write gates are the only thing standing between a request and an unapproved write to a shared system, and the ledger fallbacks keep an unanswered question from discarding loop state or staging what a sub-agent left behind. Do not mirror these rules into `../claude/`, and do not strip them here when resyncing.
- **Intentional divergence — goal and workflow-state anchoring:** `$implement`, `$implement-plan`, `$finalize`, `$quick-finalize`, and `$plan` create goals via `create_goal` and maintain one pipeline checklist per goal in a workflow file under `.turbo/workflows/`, mirroring every `update_plan` call into it. `$polish-code` and `$refine-plan` name their loop ledger in the objective of a goal they create, or register it in that workflow file with a `Loop ledger:` line. The Claude siblings have none of this: Codex compaction drops `update_plan` state, while a goal's objective is re-injected every turn from storage; Claude Code task state survives in its harness, and its loops write the ledger path into a task. Both editions share the loop ledger under `.turbo/loops/` itself: its minted identity, its discovery rule, and the reconciliation of a pending smoke-test baseline. The Claude ledger's per-iteration `open`/`awaiting`/`classified` state lines track gates this edition's loops do not have (see loop autonomy). For the same reason as the goal anchoring, `$preview` Step 5, `$prototype` Step 6, `$discuss-change` Step 5, `$draft-plan` Step 8, `$split-and-ship` Step 2, the "Edit the description first" hand-over in Phase 4 of `$pr`'s create reference, and the out-of-session hands-on check in `$draft-plan` Step 6 and `$refine-plan` Step 5 end a goal continuation turn that carries no reply from the user without calling any tool, since a continuation turn with no tool call suppresses the next one; the Claude siblings halt without it. Do not mirror the goal, workflow-state, `Loop ledger:` registry, or continuation-guard steps into `../claude/`, and do not strip them here when resyncing.
- **Intentional divergence — plan read projection:** `$implement-plan` Step 2 reads every file the plan references without the Claude edition's projection of that read's share of the context window, the question it asks above 25%, or the subagent answer its Step 3 passes to `/implement`. `$implement` Step 3 likewise omits the path that answer selects there, which hands each Implementation Step to a fresh sub-agent. The projection needs a context reading that Codex does not expose, and that question is what leads to the path. Do not mirror either into this edition when resyncing.
- **Intentional divergence — default-branch commit:** `$commit-staged` Step 2 and `$ship` Step 5 omit the Claude edition's statement that the current branch is kept and committed on, including when it is the default branch. That sentence counteracts a Claude Code system-prompt rule ("If on the default branch, branch first"); Codex has no equivalent, so it would be inert here. Do not mirror it into this edition when resyncing.
- **Intentional divergence — shared auto memory:** Setup writes the global `codex.sharedClaudeAutoMemory = true` contract only after validating the shared Claude Code memory integration, and `$self-improve` trusts that saved value for every project while resolving the source path instead of repeating setup or project-readiness checks; otherwise it uses a harness-approved memory update target or skips Auto memory. The Claude sibling writes the auto-memory directory its own harness exposes directly. Keep imported Codex extension resources read-only, preserve the Codex preference and discovery branch during resyncing, and do not add them to the Claude sibling.
- **Intentional divergence — memory consolidation:** the Claude edition's `/dream` consolidates the Claude Code auto-memory directory in place and then offers to clean up `.turbo/`. This edition reaches that directory only as the shared source `codex.sharedClaudeAutoMemory` enables, which a run of the Claude skill already covers, and its own consolidated memory files stay read-only. The `.turbo/` cleanup stays with the memory pass as one skill. Do not mirror it into this edition when resyncing.
- **Intentional divergence — out-of-checkout writes:** `$backlog` Step 3, `$self-improve` Step 6, and `$draft-plan` Step 6 leave their writes into another repo unqualified (an append, a turbo lesson handoff, and a gated plan), as do `$handoff` Step 3 and `$implement-plan` Step 4 their writes to the main checkout. The Claude siblings route them through the Edit or Write tool, which its Bash sandbox does not gate; `apply_patch` runs under the same sandbox policy as shell commands here, so it offers no equivalent escape, and [`SKILL-CONVENTIONS.md`](SKILL-CONVENTIONS.md) bars a skill from requesting a wider sandbox for routine work. Whether a denied cross-repo append fails silently here, as it does under Claude Code, and whether a main-checkout write is refused from inside a linked worktree are unverified; establish that before adding a rule. Do not mirror the Claude tool guidance into this edition, nor the refuse-and-print fallback that depends on it, which covers a write to the main checkout refused from inside a linked worktree. The worktree-aware repo-root resolution in `$backlog` and `$handoff` Step 1 carries no such dependency and is mirrored.
- **Intentional divergence — open items:** the Claude edition's plugin mod keeps a list of open items above the prompt, through a tool, a rule it injects, and a context block, and `/resolve-open-items` and the open-items `list` call in `/handoff` Step 2 build on it. This edition has no mod and no band above the prompt to list items in. Do not mirror any of them into this edition when resyncing.
- **Intentional divergence — parallel backlog split:** the Claude edition's `/implement-backlog` can hand parallel working sets to extra sessions it briefs by message, each working in a worktree of its own unless its lane only plans, and so has one more step than `$implement-backlog`. `codex queue` delivers a message to an open session, but under the sandbox it fails to start its app server or to reach the daemon socket (probed on codex-cli 0.167.1), and [`SKILL-CONVENTIONS.md`](SKILL-CONVENTIONS.md) bars a skill from requesting a wider sandbox for routine work. Do not mirror the split into this edition when resyncing; re-run the probe first.
- **Intentional divergence — sandbox-denial retry:** `$run-checks` and `$test-run-rules` omit the Claude edition's re-run of a command that failed on a sandbox denial with its Bash tool's sandbox override, and `$ship` Step 7 and `$split-and-ship` Step 2 omit its re-run of the upstream-tracking write a sandbox refused after a push. [`SKILL-CONVENTIONS.md`](SKILL-CONVENTIONS.md) bars a skill from requesting a wider sandbox for routine work. Do not mirror the retry into this edition when resyncing.
- **Intentional divergence — peer review execution:** the Claude edition's `/peer-review` runs a code review through a Codex sandbox that keeps the repository read-only and the temporary directory writable, so its peer can run test suites and mutation checks. `$peer-review` stays limited to reading, and tells the reviewer so, to name the checks it could not run, and to mark a verdict resting on reading alone: `$claude-print` confines Claude through a tool allow-list of file reads and read-only git commands, which cannot express execution that leaves the repository unwritable. Whether Claude Code's own Bash sandbox could give `claude -p` that shape from inside the Codex sandbox is unprobed; probe it before adding execution here, and do not widen the allow-list to mirror it when resyncing.
